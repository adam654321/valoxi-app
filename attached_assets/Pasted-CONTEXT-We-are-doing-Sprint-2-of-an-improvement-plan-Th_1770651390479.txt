CONTEXT: We are doing Sprint 2 of an improvement plan. This is Step 2 — reworking the fee calculation model so fees can be either percentage-based or fixed amounts.

CURRENT PROBLEM: All 5 fee types (legal DD, accounting DD, broker, loan arrangement, deal maker) are calculated as offerPrice × percent / 100. In reality, legal DD and accounting DD on UK SME deals are typically fixed/capped amounts (£15k-£40k), not percentages. Broker and deal maker fees are genuinely percentage-based. Loan arrangement fees should be based on the loan amount, not the deal price (we'll handle that in a separate step).

PROPOSED APPROACH: Add a fee "type" discriminator for each fee so the calculator knows whether to treat the value as a percentage or a fixed amount.

Before making changes, I need you to evaluate two approaches and recommend one:

APPROACH A — Add 5 new type columns to dealModels:
  feeLegalDdType: varchar('percent' | 'fixed'), default 'fixed'
  feeAccountingDdType: varchar('percent' | 'fixed'), default 'fixed'
  feeBrokerType: varchar('percent' | 'fixed'), default 'percent'
  feeLoanArrangementType: varchar('percent' | 'fixed'), default 'percent'
  feeDealMakerType: varchar('percent' | 'fixed'), default 'percent'

The existing "Percent" columns would be reinterpreted: when type is 'percent', the value is a percentage; when type is 'fixed', the value is a fixed amount in pounds. We'd probably want to rename them to remove "Percent" from the column name (e.g., feeLegalDdValue), but that's a bigger migration.

APPROACH B — Add a single JSON column feeConfig that stores all fee settings:
  feeConfig: json, default { legalDd: { type: 'fixed', value: 25000 }, accountingDd: { type: 'fixed', value: 15000 }, broker: { type: 'percent', value: 2.0 }, ... }

This is more flexible but loses individual column queryability.

For each approach, report:
1. How many files would need to change
2. Whether it would break any existing data (would a migration be needed for existing deal models?)
3. Which is simpler to implement given the existing codebase patterns

Also check: are there any frontend components that render or edit fee values? Search client/src/ for any references to feeLegalDd, feeAccountingDd, feeBroker, feeLoanArrangement, feeDealMaker and report what you find.

DO NOT MAKE ANY CHANGES. Only analyse and recommend.
