Replit has nailed the root cause in the final paragraph and it's the cleanest possible fix:

"The fetchTextContent calls should read files directly from disk. The filePath is stored in the database — completely bypassing HTTP routing and rate limiting."

The problem isn't the rate limit numbers — it's the architecture. Background processing should never be making HTTP calls back through the public API. Every fetchTextContent(fileUrl) call is a self-inflicted round trip through two rate limiters when it could just read a local file. Fix that one thing and the rate limit problem disappears entirely, permanently, regardless of document volume.
The Gemini external fetch issue (where Gemini itself fetches the public URL for non-text files) is a secondary concern we can address separately — the immediate production risk is the loopback calls.
