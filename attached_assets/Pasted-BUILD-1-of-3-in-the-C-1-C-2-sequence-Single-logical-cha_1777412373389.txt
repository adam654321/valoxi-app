BUILD 1 of 3 in the C-1/C-2 sequence. Single logical change: make refreshCsrfToken() complete before the app renders authenticated routes. This is a precondition for safely removing the CSRF bypass in Build 2.

Background: Currently in client/src/hooks/useAuth.ts, refreshCsrfToken() is fired inside a useEffect after the user query resolves but is NOT awaited. The CSRF token sits in module-level memory at client/src/lib/queryClient.ts. Pages can mount and fire mutations before the token fetch completes. This race is currently masked because the server-side CSRF middleware bypasses Clerk-authenticated requests entirely. Once that bypass is removed in Build 2, the race becomes a 403 on any mutation that fires on mount. The known case is the billing page verify-session POST when a user returns from Stripe checkout with ?session_id=... in the URL.

Fix shape: extend useAuth so that isLoading remains true until BOTH the user query AND the CSRF token fetch have resolved. Authenticated route trees in App.tsx already gate on isLoading, so this fix prevents any authenticated page mounting before the token is ready.

Implementation approach:

In client/src/lib/queryClient.ts:
- Modify refreshCsrfToken() to return a typed Promise<boolean> indicating whether the fetch succeeded.
- The current implementation already returns Promise<void>, so this is a small change. Keep the existing fetch logic, just narrow the return type and surface success/failure.

In client/src/hooks/useAuth.ts:
- Replace the existing useEffect-based fire-and-forget call to refreshCsrfToken() with a useQuery that depends on the user query.
- The new query should:
  - Have queryKey something like ["__internal__/csrf-token-bootstrap"]
  - Have queryFn that calls refreshCsrfToken() and returns a boolean
  - Have enabled: !!user (only run when user is non-null)
  - Have staleTime: Infinity and gcTime: Infinity (never refetch automatically — token is stored in module memory and refreshed by login flow only)
  - Have retry: 1 (one retry on failure, then accept the failure)
- The hook's returned isLoading should be: original isLoading OR (user is non-null AND csrfBootstrap is still loading).
- The hook's existing returned fields (user, isAuthenticated, isSystemAdmin, error, authError) must remain unchanged in shape.

Edge cases to handle:
1. Unauthenticated user (user === null): csrfBootstrap is disabled (enabled: !!user is false), so isLoading correctly returns the original auth isLoading only. Login and other public pages still render.
2. Auth error (CLERK_USER_NOT_LINKED, CLERK_USER_INACTIVE): user is undefined, csrfBootstrap is disabled. The existing authError branches in App.tsx render correctly.
3. CSRF fetch fails (network error or server 500): the bootstrap query resolves to false after retry. isLoading goes false. The user sees the authenticated app. Subsequent mutations will 403 because the token is null. This is acceptable degraded behaviour — better than blocking the user forever.
4. User logs out and back in: existing /api/v2/auth/login flow already calls refreshCsrfToken() explicitly (login.tsx line 39). After Build 1, the login flow path should still work because:

   - login.tsx calls refreshCsrfToken() explicitly

   - useAuth re-runs, user becomes non-null, csrfBootstrap query fires
   - The csrfBootstrap query will hit the cached refreshCsrfToken result (or fetch fresh — verify behaviour)
