ASSESS — Build 3 of #151. Wire confirmFirstPayment and the genuine
subscription.renewed write into the invoice.paid handler in
billing.routes.ts. READ-ONLY. Propose the diff.

Goal: this is the wiring build that makes Builds 1 and 2 actually
work end-to-end. After Build 2, the system writes neither
'subscription.activated' nor 'subscription.renewed' anywhere. Both
need to be written from the invoice.paid handler:

(a) On the FIRST paid invoice for a subscription, fire
    confirmFirstPayment(...). It writes 'subscription.activated'
    to both subscription_events and funnel_events.

(b) On EVERY subsequent paid invoice for that same subscription
    (i.e. genuine renewals), write 'subscription.renewed' directly
    via billingRepository.logEvent. Do NOT route through
    updateSubscriptionStatus's transition-aware function -- that
    function will write 'subscription.recovered' for past_due->active
    or 'subscription.updated' for active->active, and we want renewals
    to keep their dedicated label.

The two writes are mutually exclusive. confirmFirstPayment returns
{ wasFirstPayment: boolean } -- use that to decide which path.

   Notes on the design:
   - We pass invoice.id (the Stripe invoice ID, e.g. 'in_1ABC...')
     to confirmFirstPayment as the paidInvoiceId payload field.
   - When wasFirstPayment is FALSE, we know this isn't the first
     payment, but we don't yet know whether it was a genuine renewal
     (active -> active, came from a recurring billing cycle) or a
     recovery (past_due -> active after a failed payment). 
     updateSubscriptionStatus has just written 'subscription.recovered'
     for the past_due -> active case. We do NOT want to also write
     'subscription.renewed' for that case. This means the diff above
     is incomplete -- we need a guard that distinguishes "genuine
     renewal" from "recovery".
     
     Option 1: read matchingSub.status from BEFORE the
     updateSubscriptionStatus call (matchingSub is fetched earlier in
     the handler). If matchingSub.status was 'past_due', skip the
     subscription.renewed write -- it was a recovery, already labelled
     correctly by updateSubscriptionStatus.
     
     Option 2: re-fetch the most recent subscription_events row after
     updateSubscriptionStatus, check its event_type. If it's
     'subscription.recovered', skip the renewed write.
     
     Option 1 is simpler and avoids an extra query. matchingSub is
     already in scope before updateSubscriptionStatus is called, so
     its .status field reflects the previous state. Recommended.

   Refined diff:
   
     const previousStatusForRenewal = matchingSub.status;
     
     await billingService.updateSubscriptionStatus(

   My read: NO. confirmFirstPayment should fire on invoice.paid only.
   Reasoning:
   - checkout.session.completed fires before payment is collected
     (this is exactly the bug we are fixing).
   - verify-session is called from the frontend redirect after
     Stripe checkout completes, but BEFORE invoice.paid has
     necessarily been processed by our webhook. The customer may
     have technically paid (Stripe checkout is complete) but the
     webhook hasn't yet flipped state. Calling confirmFirstPayment
     here risks firing it before the corresponding invoice.paid
     webhook lands, which then would also try to fire it again
     (idempotent guard prevents double-write, so safe, but adds
     non-determinism to the audit trail timing).
   - Cleanest model: only fire from invoice.paid. Stripe is the
     source of truth for whether a payment landed.
