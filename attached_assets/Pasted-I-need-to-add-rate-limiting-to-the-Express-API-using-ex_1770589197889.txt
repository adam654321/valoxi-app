I need to add rate limiting to the Express API using express-rate-limit. This should apply different limits to different endpoint categories based on their risk profile.

1. Install the package
npm install express-rate-limit

2. Create server/middleware/rate-limit.ts
This file should export multiple rate limiter instances, each configured for a different category of endpoint:
General API limiter — applies to all /api/ routes as a baseline:

Window: 15 minutes
Max requests: 100 per window per IP
Standard error message: { message: 'Too many requests, please try again later.' }
Return 429 status code

Auth limiter — stricter limit for login and registration to prevent brute force:

Window: 15 minutes
Max requests: 10 per window per IP (login attempts)
Message: { message: 'Too many authentication attempts, please try again later.' }

Portal limiter — for unauthenticated portal endpoints:

Window: 15 minutes
Max requests: 50 per window per IP
Message: { message: 'Too many requests to the portal, please try again later.' }

Analysis trigger limiter — for AI/Gemini analysis endpoints which are expensive:

Window: 15 minutes
Max requests: 5 per window per IP
Message: { message: 'Too many analysis requests, please try again later.' }

File upload limiter — for document upload endpoints:

Window: 15 minutes
Max requests: 20 per window per IP
Message: { message: 'Too many uploads, please try again later.' }

Configuration for all limiters:

standardHeaders: 'draft-7' — sends RateLimit-* headers so the frontend can see remaining quota
legacyHeaders: false — disables the deprecated X-RateLimit-* headers
Use the default in-memory store (fine for a single-process Replit deployment — if you ever scale to multiple instances you'd switch to rate-limit-redis, but that's not needed now)
skipSuccessfulRequests: false — count all requests, not just failed ones

Export each limiter as a named export, e.g.:
typescriptexport const generalLimiter = rateLimit({ ... });
export const authLimiter = rateLimit({ ... });
export const portalLimiter = rateLimit({ ... });
export const analysisTriggerLimiter = rateLimit({ ... });
export const uploadLimiter = rateLimit({ ... });

3. Apply the general limiter in server/routes.ts
Import the generalLimiter and apply it before the modular routes are registered:
typescriptimport { generalLimiter } from './middleware/rate-limit';

// Inside registerRoutes, BEFORE registerModularRoutes:
app.use('/api/', generalLimiter);
This gives every API endpoint a baseline limit. The more specific limiters below will stack on top (a request to /api/v2/auth/login hits both the general limiter and the auth limiter).

4. Apply specific limiters in server/routes/index.ts
Import the specific limiters and apply them to the relevant route mounts. Here's the mapping — apply these at the app.use() registration lines:
Auth routes:
typescriptapp.use('/api/v2/auth', authLimiter, authRoutes);
Portal routes (the unauthenticated ones — look for any portal routes that DON'T have isAuthenticated):
typescriptapp.use('/api/v2/portal', portalLimiter, portalRoutes);
// Also apply to any public portal routes
app.use('/api/v2/public', portalLimiter, publicDocumentRoutes);
Analysis trigger routes:
typescriptapp.use('/api/v2/stage1-analysis', isAuthenticated, analysisTriggerLimiter, stage1AnalysisRoutes);
app.use('/api/v2/expert-analysis', isAuthenticated, analysisTriggerLimiter, expertAnalysisRoutes);
File upload routes:
typescriptapp.use('/api/v2/files', isAuthenticated, uploadLimiter, documentsFilesRoutes);
IMPORTANT: Keep the existing isAuthenticated middleware in place. The rate limiter is an additional layer, not a replacement. The order should be: rate limiter first (cheap check, rejects before hitting auth/DB), then auth middleware.
Actually, reconsider the ordering for authenticated routes: for those, it's better to put isAuthenticated first so unauthenticated requests get rejected with 401 before consuming rate limit quota. So for authenticated routes:
typescriptapp.use('/api/v2/stage1-analysis', isAuthenticated, analysisTriggerLimiter, stage1AnalysisRoutes);
But for unauthenticated routes (auth, portal, public), the rate limiter should come first:
typescriptapp.use('/api/v2/auth', authLimiter, authRoutes);
app.use('/api/v2/portal', portalLimiter, portalRoutes);

5. Handle the trust proxy setting
Replit (and most hosting platforms) sits behind a reverse proxy. Without configuring this, express-rate-limit will see all requests as coming from the same IP (the proxy's IP), which means the rate limit applies globally instead of per-user.
In server/routes.ts (or wherever the Express app is configured — check server/index.ts), add before any middleware:
typescriptapp.set('trust proxy', 1);
This tells Express to trust the first proxy's X-Forwarded-For header for the real client IP. Check where your Express app is created (express() call) and add it there, early, before any middleware is applied.

6. Optional: skip rate limiting in development
If you find rate limiting annoying during local development, you can conditionally skip it. In rate-limit.ts, you could add:
typescriptconst isDev = process.env.NODE_ENV !== 'production';
And set higher limits in dev, or use skip: () => isDev in the limiter config. But I'd recommend keeping it active in dev too so you catch any issues before production. Up to you — if you do add a dev skip, only apply it to the general limiter, NOT the auth limiter.

Testing checklist:

App starts without errors
Normal usage works fine (browsing, clicking through pages doesn't hit limits)
Check response headers on any API call — you should see RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset headers
Test the auth limiter: attempt 11 rapid logins (can use browser dev tools or curl) — the 11th should return 429
Test the portal limiter: hit a portal endpoint repeatedly — should get 429 after 50 requests in 15 minutes
Verify the trust proxy setting is working: check that rate limiting is per-client-IP, not global. You can verify by checking the RateLimit-Remaining header — it should only decrease for YOUR requests, not for other users' requests
Confirm that hitting a rate limit returns a proper JSON response (not an HTML error page)

Do NOT:

Change any endpoint logic or response formats
Remove isAuthenticated from any routes
Add rate limiting to WebSocket connections (that's a different mechanism)
