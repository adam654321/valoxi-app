Cycle 5 assess. Extend waitlistRepository with methods needed for admin waitlist management. READ ONLY, do not change any code. Report back with findings.
PROPOSED CHANGE SUMMARY
The existing waitlistRepository has two methods: getByEmail and create. Cycle 6 needs the admin to list waitlist entries with filtering, look up a single entry by id, update status, and atomically mark an entry as invited with audit fields populated. This cycle adds the methods without changing any existing behaviour.
PROPOSED NEW METHODS

list(filters)

Returns Waitlist[] (array)
Filter by status (optional): string matching 'new' | 'approved' | 'invited' | 'declined'
Pagination: limit (default 50, max 200) and offset (default 0)
Order by createdAt DESC
No totalCount return in this cycle (can add in Cycle 6 if the UI needs it, or if the UI does simple paging it's not needed)


getById(id)

Takes a uuid string
Returns Waitlist | undefined


updateStatus(id, status, adminUserId)

Updates status, statusChangedAt (NOW), statusChangedBy (adminUserId)
Returns Waitlist | undefined
Used for 'approved' and 'declined' transitions, not 'invited' (that has its own method below)


markInvited(id, adminUserId, invitedUserId)

Updates status to 'invited', statusChangedAt (NOW), statusChangedBy (adminUserId), invitedUserId
Returns Waitlist | undefined
Distinct from updateStatus because it sets invitedUserId in the same write



All four methods are thin Drizzle wrappers, matching the style of the existing two methods.
