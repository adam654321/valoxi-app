BUILD 3 of 3 in the C-1/C-2 sequence. Single logical change: add Origin/Referer header validation as defence-in-depth on /api/v2 non-GET requests.

Background: Builds 1 and 2 have shipped to dev. CSRF middleware is now properly enforced for all authenticated requests. The C-1 finding is closed.

C-2 is the defence-in-depth layer that pairs with CSRF. CSRF protection works only if the token check is correct. Origin validation is the second wall: it blocks cross-site writes at the HTTP layer regardless of cookie or token state. If any future code change accidentally weakens CSRF, Origin still rejects malicious cross-origin requests.

The fix is to add a new middleware that:
- Checks Origin header first, falls back to Referer
- Compares against an allowlist sourced from process.env.APP_URL plus process.env.REPLIT_DOMAINS (comma-separated list, all entries included)
- Skips GET, HEAD, OPTIONS (no CSRF risk)
- Skips webhook endpoints which legitimately have no Origin (Stripe and Clerk webhooks rely on signature verification)
- Strips trailing slashes during comparison (dev APP_URL has trailing slash, prod does not, browser Origin headers never do)
- Rejects with 403 if Origin/Referer is missing or does not match the allowlist

Allowlist construction (must be deterministic):
- Read process.env.APP_URL once at module load
- Read process.env.REPLIT_DOMAINS once at module load (may be undefined or comma-separated list)
- For each value, parse via new URL(value).origin to get the canonical origin string (scheme + host + port). This handles trailing slashes automatically because new URL strips paths.
- If APP_URL is unset, fall through to REPLIT_DOMAINS only.
- If both are unset, log a warning at startup and accept all origins (do NOT fail closed at module load — that would brick any future deployment that forgot to set the var). The Stripe webhook and Clerk webhook routes are protected by signature verification regardless. The CSRF token is the primary defence.
- Build a Set<string> of canonical origins for O(1) comparison.

Middleware logic:
- If req.method is GET, HEAD, or OPTIONS, return next() immediately
- Read req.headers.origin, fall back to req.headers.referer
- If both absent, return 403 with body { success: false, message: 'Origin validation failed', code: 'ORIGIN_ERROR' }
- For Referer: parse via new URL(referer).origin to extract just the origin part (referers contain full URLs with paths)
- Compare the resolved origin against the allowlist Set
- If not in allowlist, return 403 with the same body
- If allowlist is empty (env vars not set, fail-open mode), warn-log once and call next()
- Otherwise call next()

Mount:
In server/routes.ts, mount the new middleware on /api/v2 immediately after attachCsrfToken (line 13) and before registerModularRoutes (line 15). The mount path /api/v2 means it does not apply to webhooks at /api/v2/billing/webhook/stripe or /api/v2/webhooks/clerk because those mounts in server/index.ts use express.raw and bypass the JSON parser, but they DO still go through middleware mounted on /api/v2. Therefore the middleware itself MUST check req.path and skip the two webhook paths explicitly, OR the mount in routes.ts must use a regex that excludes them.

Cleaner approach: add the path-skip logic inside the middleware. Specifically:
- if (req.path === '/billing/webhook/stripe' || req.path === '/webhooks/clerk') return next()
- Note req.path here is relative to the /api/v2 mount, so it does not include the /api/v2 prefix

Naming: export the middleware as validateOrigin in server/middleware/csrf.ts (same file as validateCsrfToken because they are conceptually paired). If the file gets too cluttered, can split later.
