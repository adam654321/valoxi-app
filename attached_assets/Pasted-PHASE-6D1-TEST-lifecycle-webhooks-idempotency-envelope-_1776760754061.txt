Step 5 - DB verification queries

Run all six and paste output verbatim.

A. webhook_events.stripe_event_id is populated for new rows

  SELECT id, stripe_event_id, event_type, status, created_at
  FROM webhook_events
  WHERE created_at > NOW() - INTERVAL '20 minutes'
  ORDER BY created_at DESC LIMIT 30;

  Expected: every new row has a non-null stripe_event_id starting with evt_.

B. status breakdown for the test window

  SELECT event_type, status, COUNT(1)
  FROM webhook_events
  WHERE created_at > NOW() - INTERVAL '20 minutes'
  GROUP BY event_type, status
  ORDER BY event_type, status;

  Expected: each lifecycle event_type has 1 row at status='processed' and
  2 rows at status='skipped' (from the two resends). Possibly extra
  'processed' rows from cascaded events fired by Stripe triggers.

C. subscription_events idempotency check

  SELECT stripe_event_id, COUNT(1)
  FROM subscription_events
  WHERE stripe_event_id IS NOT NULL
  GROUP BY stripe_event_id
  HAVING COUNT(1) > 1;

  Expected: zero rows. ON CONFLICT must hold.

D. subscription_events writes during the test window

  SELECT id, stripe_event_id, event_type, processed_at
  FROM subscription_events
  WHERE processed_at > NOW() - INTERVAL '20 minutes'
  ORDER BY processed_at DESC LIMIT 20;

  Note: stripe trigger uses fresh sub_xxx that do not exist in dev DB,
  so most lifecycle events will not produce a subscription_events row.
  This query exists to confirm anything that does write writes correctly.

E. Final counts vs baseline

  SELECT COUNT(1) FROM webhook_events;
  SELECT COUNT(1) FROM subscription_events;

F. Server log inspection

  In the server console output for the test window, confirm:
  - No 'Failed to log webhook event' errors.
  - No unhandled Promise rejections.
  - No TypeScript runtime errors from the handlers.
