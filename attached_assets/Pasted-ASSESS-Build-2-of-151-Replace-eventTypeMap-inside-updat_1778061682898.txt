Goal: the current eventTypeMap (lines ~233-240 of billing.service.ts)
maps every transition by newStatus alone. This is wrong because:
- active means different things depending on previousStatus (trial
  conversion vs recovery from past_due vs reactivation vs routine).
- 'subscription.renewed' is the wrong label for everything except
  the active -> active case (and even that case is suspect — true
  renewals come via invoice.paid, not customer.subscription.updated).

This build replaces the map with a transition-aware function. The
genuine 'subscription.renewed' label is REMOVED from this function
entirely. Build 3 will write 'subscription.renewed' directly inside
the invoice.paid handler in billing.routes.ts.

2. Propose the diff. Replace the eventTypeMap declaration and the
   logEvent call that uses eventTypeMap[data.status] with a private
   helper method called from logEvent. Helper signature:

     private getTransitionEventType(
       previousStatus: SubscriptionStatus | null,
       newStatus: SubscriptionStatus
     ): string

   Mapping logic, in this exact order (first match wins):
   
   - newStatus === 'past_due':           return 'invoice.payment_failed'
   - newStatus === 'canceled':           return 'subscription.canceled'
   - newStatus === 'admin_comped':       return 'admin.comp_granted'
   - newStatus === 'incomplete':         return 'subscription.incomplete'
   - newStatus === 'trialing':           return 'subscription.trialing'
   - newStatus === 'active':
       - previousStatus === 'trialing':  return 'subscription.trial_converted'
       - previousStatus === 'past_due':  return 'subscription.recovered'
       - previousStatus === 'canceled':  return 'subscription.reactivated'
       - previousStatus === 'active':    return 'subscription.updated'
       - previousStatus === null:        return 'subscription.updated'
       - default:                        return 'subscription.updated'
   - default fallback:                   return `status.changed_to.${newStatus}`

   Important: 'subscription.renewed' DOES NOT APPEAR in this function.
   Genuine renewals are written by Build 3 directly from the
   invoice.paid handler in billing.routes.ts.

   D2.1. The active -> active case currently maps to

         existing behaviour for unmapped statuses. Worth preserving
         even though all current statuses are now explicitly mapped,
         because future status enum additions would otherwise silently
         drop into a confusing label.
         
         (A) Keep the fallback.
         (B) Throw an error to force explicit mapping of new statuses.
         
         Recommended: (A). Throwing in a webhook handler risks not
         processing the event at all. A weird but logged label is
         better than a 500 response to Stripe.
