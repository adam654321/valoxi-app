PHASE 6D2 TEST PHASE 5 - Day 14 auto-cancel

WARNING: This phase calls stripe.subscriptions.cancel() against the real
ADJV test mode sub_1TOUG42N2rRCsCfrdzdaN9WB. The sub is permanently
destroyed in Stripe. After this phase, sub 30 is gone from both Stripe
and (after webhook arrives) local DB. This is intentional - we will
create a fresh sub through real checkout for 6E.

Step 5.1 - Pre-flight baseline

  SELECT id, status, past_due_since, dunning_day7_email_sent_at,
         stripe_subscription_id
  FROM subscriptions WHERE id = 30;

  Confirm: status=past_due, past_due_since recent (just set in Phase 4.3),
  stripe_subscription_id = sub_1TOUG42N2rRCsCfrdzdaN9WB.

Step 5.2 - Time-travel sub 30 to past_due 14+ days ago

  UPDATE subscriptions
  SET past_due_since = NOW() - INTERVAL '14 days 1 hour',
      dunning_day7_email_sent_at = NOW() - INTERVAL '7 days'
  WHERE id = 30;

  Verify:
    SELECT id, status, past_due_since, dunning_day7_email_sent_at
    FROM subscriptions WHERE id = 30;
  Expected: past_due_since ~14 days ago, dunning_day7_email_sent_at ~7 days ago.

Step 5.3 - Write and run the day-14 cron test script

  Create server/scripts/test-dunning-day14.ts following the same pattern
  as the day-7 script Replit wrote in Phase 2. It should import and call
  runDunningCancellationJob() directly. If runDunningCancellationJob is
  not exported from billing.cron.ts, export it (named export, not default).

  Run: npx tsx server/scripts/test-dunning-day14.ts

  Expected console output (rough):
    [billing-cron] Day-14 dunning auto-cancel: 1 candidate(s)
    [billing-cron] Stripe sub sub_1TOUG42N2rRCsCfrdzdaN9WB cancelled (dunning) for company 30

  If the script reports zero candidates, time-travel didn't take. Re-check
  Step 5.2.

Step 5.4 - Wait ~10 seconds for Stripe to send customer.subscription.deleted

Step 5.5 - Verification queries

  Query A - audit row written before Stripe cancel:
    SELECT id, stripe_event_id, event_type, processed_at, payload
    FROM subscription_events
    WHERE user_company_id = 30
      AND event_type = 'dunning.auto_cancel_requested'
      AND processed_at > NOW() - INTERVAL '5 minutes';
    Expected: 1 row, payload contains stripeSubscriptionId, graceDays: 14.

  Query B - webhook arrived:
    SELECT id, stripe_event_id, event_type, status, created_at
    FROM webhook_events
    WHERE event_type = 'customer.subscription.deleted'
      AND created_at > NOW() - INTERVAL '5 minutes';
    Expected: 1 row, status=processed.

  Query C - local DB now canceled, dunning fields cleared:
    SELECT id, status, past_due_since, dunning_day7_email_sent_at,
           stripe_subscription_id
    FROM subscriptions WHERE id = 30;
    Expected: status=canceled, past_due_since=NULL,
              dunning_day7_email_sent_at=NULL.

  Query D - cancellation email audit row written (proves the
  hasRecentEvent gate worked):
    SELECT id, stripe_event_id, event_type, previous_status, new_status,
           processed_at
    FROM subscription_events
    WHERE user_company_id = 30
      AND event_type IN ('subscription.canceled', 'dunning.cancellation_email_sent')
      AND processed_at > NOW() - INTERVAL '5 minutes'
    ORDER BY processed_at;
    Expected: 2 rows, both event types present.

  Query E - server log scan, last 5 minutes
    Confirm:
    - "[billing-cron] Day-14 dunning auto-cancel: 1 candidate(s)" log line
    - "[billing-cron] Stripe sub sub_xxx cancelled (dunning) for company 30"
    - customer.subscription.deleted handler ran without error
    - sendDunningCancellationEmail success (or whatever the legacyEmailService
      success log looks like)
    - No errors

  Adam will separately confirm the cancellation email arrived in
  adamauty@me.com. Subject expected:
    "Your Valoxi PROFESSIONAL subscription has been cancelled"
