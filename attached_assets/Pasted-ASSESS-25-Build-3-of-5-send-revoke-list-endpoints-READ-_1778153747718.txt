Send API:
  Method: POST
  URL:    {NYLAS_API_URI}/v3/grants/<grantId>/messages/send
  Headers:
    Authorization: Bearer <NYLAS_API_KEY>
    Content-Type: application/json
    Accept: application/json
  Minimum body:
    {
      "subject": "...",
      "to": [{ "name": "...", "email": "..." }],
      "body": "<html or plain text>"
    }
  
  CRITICAL: `from` is OPTIONAL. By default Nylas sends from the
  grant's connected email address — exactly what Valoxi wants for
  personalised user-sent emails. Only set `from` for a display-name
  override; the email address still has to match the connected
  account (provider rules).

Send API errors to handle:
- 404 on grant: grant deleted upstream → mark broken, surface
  re-connect UI later
- 401 on grant: token revoked by user at provider → same as above
- 4xx quota_exceeded / rate_limit_exceeded → sandbox tier limits;
  log and rethrow
- 5xx: log and rethrow for caller to retry

Use the SDK helper nylas.messages.send(...) per CC's documented
Node SDK shape:

  await nylas.messages.send({
    identifier: grantId,
    requestBody: {
      subject: '...',
      to: [{ email: '...', name: '...' }],
      body: '...',
    },
  });

The SDK wraps the same endpoint with typed inputs/outputs.

Revoke API:
  Method: DELETE
  URL:    {NYLAS_API_URI}/v3/grants/<grantId>
  Headers: Authorization: Bearer <NYLAS_API_KEY>
  
  Returns 200 on success, 404 if grant already gone (treat as
  success — idempotent revoke).
  
  SDK equivalent: nylas.grants.destroy({ grantId })

  sendEmail:

    async sendEmail(grantId: string, payload: {
      subject: string;
      to: { email: string; name?: string }[];
      body: string;
      cc?: { email: string; name?: string }[];
      bcc?: { email: string; name?: string }[];
      replyTo?: { email: string; name?: string }[];
      isPlainText?: boolean;
    }): Promise<{ messageId: string; threadId: string | null }> {
      const client = this.getClient();
      
      try {
        const response = await client.messages.send({
          identifier: grantId,
          requestBody: {
            subject: payload.subject,
            to: payload.to,
            body: payload.body,
            cc: payload.cc,
            bcc: payload.bcc,
            replyTo: payload.replyTo,
            // SDK uses snake_case at API but typically camelCase in TS;
            // confirm via T1 whether isPlaintext or is_plaintext is the
            // correct property name.
            ...(payload.isPlainText !== undefined ? { isPlaintext: payload.isPlainText } : {}),
          },
        });
        
        // SDK wraps response in { data, requestId } typically; T1 confirms
        // the actual shape. Adjust below if needed:
        const message = (response as any).data ?? response;
        
        return {
          messageId: message.id,
          threadId: message.threadId ?? message.thread_id ?? null,
        };
      } catch (err: any) {
        // Nylas SDK errors typically carry .statusCode or .status
        const upstreamStatus = err?.statusCode ?? err?.status ?? 0;
        
        if (upstreamStatus === 401 || upstreamStatus === 404) {
          throw new NylasGrantBrokenError(
            `Grant ${grantId} returned ${upstreamStatus} from Nylas — likely revoked at provider`,
            grantId,
            upstreamStatus,
          );
        }
        
        // Quota/rate limits and 5xx: log and rethrow
        console.error(`[NYLAS] sendEmail failed for grant ${grantId}:`, err);
        throw err;
      }
    }

  revokeGrant:

    async revokeGrant(grantId: string): Promise<void> {
      const client = this.getClient();
      
      try {
        await client.grants.destroy({ grantId });
      } catch (err: any) {
        const upstreamStatus = err?.statusCode ?? err?.status ?? 0;
        
        // 404 = already gone upstream — treat as success (idempotent revoke)
        if (upstreamStatus === 404) {
          console.log(`[NYLAS] revokeGrant: grant ${grantId} already gone upstream, treating as success`);
          return;
        }
        
        console.error(`[NYLAS] revokeGrant failed for grant ${grantId}:`, err);
        throw err;
      }
    }

    router.delete('/grants/:id', async (req: Request, res: Response) => {
      try {
        const userId = req.session.userId;
        if (!userId) {
          return res.status(401).json({ success: false, error: 'Not authenticated' });
        }
        
        const grantRowId = parseInt(req.params.id, 10);
        if (isNaN(grantRowId)) {
          return res.status(400).json({ success: false, error: 'Invalid grant id' });
        }
        
        const grant = await nylasRepository.getGrantById(grantRowId);
        if (!grant) {
          return res.status(404).json({ success: false, error: 'Grant not found' });
        }
        
        // Tenant scoping: only the owning user can revoke their own grant
        if (grant.userId !== userId) {
          return res.status(403).json({ success: false, error: 'Access denied' });
        }
        
        await nylasService.revokeGrant(grant.grantId);
        await nylasRepository.markRevoked(grant.grantId);
        
        return res.json({ success: true, data: { id: grant.id, status: 'revoked' } });
      } catch (err) {
        console.error('[NYLAS] DELETE /grants failed:', err);
        return res.status(500).json({ success: false, error: 'Failed to revoke grant' });
      }
    });

DECISIONS NEEDED FROM ADAM:

D3.1. Send endpoint: should it accept the grant ROW id (1, 2, ...)
      or the Nylas grant_id (UUID like 536d7f3a-...)?
      (A) Row id (current proposal). Cleaner FK semantics, smaller
          API surface.
      (B) Nylas grant_id. More direct mapping to Nylas itself,
          allows callers to track grants without DB round-trip.
      Recommended: (A). Row id is the natural primary key.

D3.2. List endpoint: should it return scopes to the frontend?
      (A) Yes (current proposal). Useful for debug UI showing
          "what permissions did I grant".
      (B) No, omit scopes — keep the response minimal.
      Recommended: (A). Adds 1-2KB per response, useful for support
      diagnostics.

D3.3. Send endpoint: should we cap the body size?
      (A) No cap (current proposal). Trust the underlying provider
          to handle their own size limits (Gmail ~25MB, Outlook ~20MB
          including attachments).
      (B) Cap at e.g. 1MB body to prevent runaway requests early.
      Recommended: (A) for now. Build 3 doesn't handle attachments
      yet (separate concern). When attachments land in a later build,
      revisit body+attachment size limits together.

D3.4. Should send writes to a new `nylas_sends` audit table?
      (A) No, just bump lastUsedAt and log success (current proposal).
          Build 5 (document delivery integration) can add specific
          tracking when wiring NDA / offer letter / portal invitation
          sends — those have their own existing audit tables.
      (B) Yes, add a nylas_sends table now logging messageId,
          threadId, recipients, subject, sentAt, grantId for global
          audit.
      Recommended: (A). Premature for Build 3. Build 5's domain
      tables (document_deliveries, portal_invitations) already track
      who-sent-what-when. A dedicated nylas_sends table would
      duplicate that.
