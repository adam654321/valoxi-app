# Workstream 4: Auto-Trigger Stage 1 Expert Analysis When All 10 Documents Are Uploaded AND Analysed

## Context

When documents are uploaded for a target company, each one is classified and analysed by Gemini (in `server/services/file-analysis.service.ts` → `analyzeUploadedFileWithGemini()`). At the end of that function, there is already logic that auto-triggers **Stage 1** (Data Quality + Screening) when financial documents are first detected.

Currently this trigger fires too early — it triggers as soon as any company_accounts or profit_and_loss document exists. We want it to wait until ALL 10 required documents are uploaded AND have completed their Gemini document analysis (classification + data extraction).

The full expert deep dive (Phase 2) always remains a manual user decision — this workstream does NOT auto-trigger Phase 2.

## The 10 Required Documents

The completion logic already exists in `server/services/document-analysis.service.ts` → the private `calculateCompletionStatus()` method. It tracks:
- 5× Company Accounts (company_accounts_1 through company_accounts_5)
- 1× Asset Register
- 1× Sales Ledger
- 1× Staff Matrix
- 1× Profit & Loss
- 1× Balance Sheet

When `isComplete === true` (i.e. `completedCount === 10`), all document types are covered.

**Important distinction:** "present" means the document file has been uploaded. "Analysed" means Gemini has successfully classified it and extracted data (i.e. there is a row in `document_analysis_results` for that document). Both must be true for all 10 before Stage 1 auto-triggers.

**Change 2:** Add a new public method to find documents that are uploaded but missing their Gemini analysis:

```typescript
/**
 * Returns document IDs that exist in the documents table for this company
 * but do NOT have any corresponding rows in document_analysis_results.
 * Used to identify documents that need their analysis re-triggered.
 */
async getDocumentsMissingAnalysis(targetCompanyId: number): Promise<number[]> {
  const allDocuments = await documentAnalysisRepository.getAllDocumentsForCompany(targetCompanyId);
  const missingAnalysis: number[] = [];
  
  for (const doc of allDocuments) {
    const analysisResults = await documentAnalysisRepository.getAnalysisResultsByDocumentId(doc.id);
    if (!analysisResults || analysisResults.length === 0) {
      missingAnalysis.push(doc.id);
    }
  }
  
  return missingAnalysis;
}
```

  const [event] = await db
    .select()
    .from(fileUploadEvents)
    .where(eq(fileUploadEvents.documentId, documentId))

## Two Paths to Stage 1

There are two ways Stage 1 can be triggered:

### Path A: Automatic (all 10 documents)
1. After EVERY document analysis completes, check: are all 10 document types present?
2. If NO → log the count and do nothing (wait for more uploads)
3. If YES → check: do all uploaded documents have completed analysis results?
4. If some are MISSING analysis → re-trigger Gemini analysis for those specific documents (they will loop back through this check when done)
5. If ALL analysed → check: has Stage 1 already run or is it running?
6. If NOT → auto-trigger Stage 1 (Data Quality + Screening) only

### Path B: Manual bypass ("Progress to Analysis" button)
The "Progress to Analysis" button in the `AnalysisCompletionIndicator` component is a **manual override**. It exists because not every company will have all 10 documents (e.g. a company trading for only 4 years will have 3 years of accounts, not 5). When the user clicks this button:

1. It calls the API route `/api/v2/expert-analysis/trigger-stage1/:id` directly
2. This goes straight to `expertAnalysisService.triggerNewStage1Pipeline()` — it does NOT pass through the file-analysis auto-trigger logic
3. The 10/10 completion check is completely bypassed — Stage 1 runs with whatever documents are available

**This already works correctly** because the manual button calls the API route directly, which has no completion checks. The auto-trigger logic only lives inside `file-analysis.service.ts` and only runs after individual document analyses complete. These are two completely separate code paths.

**Critical: Do NOT add any completion checks to the API route or the `triggerNewStage1Pipeline` method.** These must remain callable at any time regardless of document count. The completion gating is ONLY in the auto-trigger path.

Once Stage 1 has been triggered (by either path), the `hasCompletedScreening` / `hasRunningExperts` checks in the auto-trigger logic prevent it from re-running.

Stage 2 (full expert deep dive) is ALWAYS a manual user decision via the existing "Start Expert Deep Dive" button — neither path auto-triggers it.

## Important Notes

- Do NOT remove any manual trigger buttons — the "Progress to Analysis" button, "Start Expert Deep Dive" button, retry/cancel controls all remain exactly as they are
- Do NOT auto-trigger Stage 2 (the full deep dive) under any circumstances
- Do NOT add completion checks to the expert-analysis API routes or service methods — they must remain callable regardless of document count
- The re-trigger for missing analyses is fire-and-forget — each re-triggered analysis will call `analyzeUploadedFileWithGemini` again, which will re-check completion at the end, creating a natural convergence loop
- The `hasCompletedScreening` check prevents re-triggering Stage 1 on subsequent uploads after screening has already run (whether it was triggered automatically or manually)
- The `hasRunningExperts` check prevents duplicate triggers if Stage 1 is already in progress
