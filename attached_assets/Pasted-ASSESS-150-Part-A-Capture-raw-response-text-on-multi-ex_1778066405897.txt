PROPOSED DIFF (after diagnostic tasks):

The fix has two parts: surface the raw text and usage from
gemini-expert-service when parse fails, and persist it in
runExpert's catch.

Part 1: gemini-expert-service.ts

Replace this block:
    if (!response.json) {
      throw new Error(`Failed to parse ${expertType} expert response as JSON`);
    }

With a custom error class that carries the raw response and usage.
Define the class at top of file:

    export class GeminiParseFailureError extends Error {
      constructor(
        message: string,
        public readonly rawText: string,
        public readonly usage: ExpertAnalysisUsage,
      ) {
        super(message);
        this.name = 'GeminiParseFailureError';
      }
    }

And throw it instead:

    if (!response.json) {
      const usage: ExpertAnalysisUsage = response.usage
        ? {
            promptTokenCount: response.usage.promptTokens,
            candidatesTokenCount: response.usage.candidateTokens,
            totalTokenCount: response.usage.totalTokens,
          }
        : {};
      throw new GeminiParseFailureError(
        `Failed to parse ${expertType} expert response as JSON`,
        response.text,
        usage,
      );
    }

Part 2: expert-analysis.service.ts

Import the new error class:

    import { GeminiExpertService, GeminiParseFailureError } from './gemini-expert-service';

In runExpert's catch block, branch on error type:

    } catch (error) {
      const processingTime = Date.now() - startTime;
      console.error(
        `[EXPERT_ORCHESTRATOR] ${expertType} failed for company ${record.targetCompanyId}:`,
        error
      );
      
      const RAW_RESPONSE_CAP_BYTES = 100_000;
      
      if (error instanceof GeminiParseFailureError) {
        const rawText = error.rawText.length > RAW_RESPONSE_CAP_BYTES
          ? error.rawText.slice(0, RAW_RESPONSE_CAP_BYTES) + '...[truncated]'
          : error.rawText;
        
        await this.updateExpertRecord(record.id, {
          status: 'failed',
          processingTime,
          usageMetadata: error.usage,
          analysisData: {
            error: error.message,
            failure_type: 'parse_failure',
            raw_response: rawText,
            raw_response_length: error.rawText.length,
          },
        });
      } else {
        await this.updateExpertRecord(record.id, {
          status: 'failed',
          processingTime,
          analysisData: {
            error: error instanceof Error ? error.message : 'Unknown error',
          },
        });
      }
    }

DECISIONS NEEDED FROM ADAM:

D150A.1. Cap size for raw_response.
  (A) 100KB hard cap. Sufficient for 16k-token outputs at ~6 bytes/
      token. Truncated with '...[truncated]' marker.
  (B) 50KB cap. More conservative, may truncate full synthesis output.
  (C) Uncapped. Risk: runaway model could produce multi-MB rows.
  Recommended: (A).

D150A.2. Where to store raw_response.
  (A) Inside analysis_data.raw_response sub-field. No schema change.
      Keeps related data co-located. Slightly less structured.
  (B) New column raw_response_text on expert_analysis_results.
      Cleaner schema, requires migration.
  Recommended: (A). Avoids migration. Keeps the diff to two files.

D150A.3. Backfill scope.
  (A) Forward-only fix. Past failures stay un-debuggable. Future
      failures (~1-3/week given current rates) will be investigable.
  (B) Re-run all 17 affected companies' failed analyses to capture
      raw responses now. Costs Gemini API spend but immediate evidence.
  (C) Wait for natural reruns when affected customers retry.
  Recommended: (A) for this build, with (C) as the practical follow-on
  (customers will naturally retry; we capture evidence as they do).

D150A.4. Should usage_metadata be written on ALL failure paths or
         only parse_failure?
  (A) Only parse_failure (as in proposed diff). Other failures
      (network, timeout, rate limit) don't have a meaningful usage
      to report.
  (B) Write usage_metadata on every failure path that has a usage
      object available, even non-parse failures.
  Recommended: (A). Other failures don't get a response at all,
  so there's no usage to capture.
